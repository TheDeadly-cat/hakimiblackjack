# V0.3c 实时捕获（授权窗口 / 显示器）

目标：把「只能读已录好的文件」变成「能盯住一个正在播放的授权窗口」，
并且把帧原样交给已有识别管线，不另起一套识别。

本轮交付的是**采集与接线**，不是识牌达标。真实牌桌的点数识别仍未通过，
见本文末尾「已知不支持」。

## 选型与理由

唯一主采集后端：**Windows Graphics Capture**，经 `windows-capture==2.0.1`
（Rust/PyO3，MIT，轮子 `cp39-abi3-win_amd64`，因此 Python 3.14 可直接装）。

同一个后端同时覆盖两种来源，因此不需要再造第二套采集器：

| 来源 | 用途 | 特点 |
|---|---|---|
| 窗口 | 默认。盯住浏览器窗口 | 被别的窗口盖住仍能捕获；只录该窗口，不会拍到余额、聊天、通知；本程序预览不会被卷进去 |
| 显示器 | 备选。框选一块屏幕区域 | 窗口被遮挡时会拍到上层内容 |

没有采用 DXcam：桌面复制只能按显示器取图，遮挡即失效，且最后一次发版在 2022 年。
没有采用 GDI `PrintWindow`：对硬件加速的视频层经常返回黑帧，不适合盯视频。

界面继续用 Tkinter，不改写成 PySide6：现有 `ui/app.py`（55KB）与
`ui/vision_panel.py` 能满足目标，重写没有对应收益。

## 本机实测行为（Windows 11 build 26200，RTX 5060，Python 3.14.6）

| 项目 | 实测 |
|---|---|
| 显示器捕获 | 2560×1440 BGRA，4.04 秒 184 帧，首帧 219ms，非全黑 |
| 窗口捕获（静止 Chrome） | 5 秒 **1 帧** |
| 阻塞式 `start()`（静止窗口） | 不返回，必须强杀 |
| 取帧时帧龄 | p50 = p95 = 15.6ms |
| 最小显示器序号 | 1（传 0 被后端拒绝） |

这些数字是本机一次实测，不是承诺速率，也不代表真实牌桌下的表现。

### 三条必须照着设计的性质

1. **变化驱动**：画面不动就没有新帧。「暂无新帧」与「捕获失败」是两种状态，
   界面必须分开显示，不能把视频暂停说成捕获挂了。
2. **只能自由线程启动**：阻塞式 `start()` 在没有新帧时不返回，
   因此一律 `start_free_threaded()`，UI 线程不等采集。
3. **缓冲会被复用**：回调拿到的是采集后端的内存视图，返回后就会被下一帧覆盖。
   `FrameIntake.offer()` 必须复制出独占像素（用 `.copy()`，
   不能用 `ascontiguousarray`——已连续时它会原样返回视图，等于没复制）。

## 模块边界

```
capture/                     不认识牌面，不导入 vision / ledger / ui
  contracts.py     FramePacket、GenerationToken、状态常量、内容签名
  window_list.py   ctypes 枚举窗口（不新增依赖），排除本进程窗口
  frame_intake.py  采样、裁区、取得所有权、重复帧、有界队列、换代
  wgc_source.py    WGC 适配层：自由线程、生命周期、来源消失检测

vision/live_input.py         不导入 capture：帧按 FrameLike 结构约定传入
```

两个方向都有测试把关（`tests/test_vision_live_input.py::TestModuleBoundaries`）：
vision 不许出现 `blackjack_lab.capture`，capture 不许出现 vision / ledger / ui。
因此没装 `windows-capture` 时识别侧照样能导入。

## 单显示器怎么摆：记牌器可以盖在牌桌上

本机只有一个 2560×1440 显示器，牌桌全屏后必须把记牌器叠上去。
`scripts/probe_overlay_capture.py` 实测（自建两个窗口，不碰真实牌桌）：

| 阶段 | 采样帧 | 看到目标颜色 | 串入遮挡窗口颜色 |
|---|---|---|---|
| 无遮挡 | 16 | 16 | 0 |
| 置顶窗口**完全盖住** | 16 | 16 | **0** |

结论：窗口捕获取的是那个窗口自己的合成内容，不是屏幕上那块区域。
所以记牌器浮窗即使压在牌面上，也不会进入捕获画面，更不会被当成牌。
这是选窗口捕获而不是显示器区域捕获的主要收益。

两个仍未验证的前提：

- 本实验用的是 Tk 窗口。浏览器有「窗口被**完全**遮挡就降帧甚至停画」的省电策略，
  因此记牌器应当做成紧凑浮窗，不要铺满整个浏览器窗口。需用真实牌桌窗口复测。
- 不要把牌桌放到另一个虚拟桌面：切走后窗口会被 DWM 标记为 cloaked，
  既可能停止渲染，也不在可选窗口清单里。

由此定下的界面取向：牌桌全屏时不需要在记牌器里再放一块大预览
（你眼睛已经在看真牌桌了），浮窗只显示识别结果与待确认项；
预览只在标定时展开。

## 坐标：归一化，不再写死像素

`navy_live_felt_v1.json` 把裁区写成 2560×1440 下的
`{x:95, y:448, w:1180, h:542}`，窗口一挪一缩放就全错。

实时样式 `LiveStyle` 改为全部存归一化比例（0–1），按当前帧宽高换算：

- `layout_version = hash(标定内容 + 当前帧宽高)`。标定改了或画面尺寸变了，版本就变。
- `stream_epoch` 在切源、改区域、改标定、来源尺寸变化时前进，队列里的旧帧一并丢弃。
- `GenerationToken = (source_id, stream_epoch, layout_version)`，
  后台结果回来前重新核对，UI 刷新成功与否不影响旧结果作废。

## 帧完整性怎么记

- `arrived` / `accepted` / `dropped_by_sampling` / `dropped_by_queue` 分别计数，
  不只报一个 FPS。到达帧率由画面变化驱动，采样帧率才是识别输入。
- `frame_content_signature` 按行采样（每 16 行）做 blake2b。
  这是重复帧判据，不是密码学证明，也不是牌面正确性证据。
- `is_repeat` 为真时，上层不得把这帧算作新的独立支持帧。
- 队列默认保留 2 帧；`latest()` 只交最新一帧，被跳过的那帧计入丢帧，
  不假装观察完整。

## 验证

```
python -m unittest tests.test_capture_intake tests.test_vision_live_input tests.test_vision_live_pipeline -q
python scripts/verify_live_capture.py --output .local-evidence/<唯一目录>
python scripts/live_capture_probe.py --list
python scripts/live_capture_probe.py --window <句柄> --seconds 10
```

`verify_live_capture.py` 自己开一个已知颜色的测试窗口再捕获它，
因此不碰任何真实牌桌、账号或桌面内容，又能验证真东西。本机 9 项全通过：
像素与已知颜色一致、多帧到达、静止时报「暂无新帧」而不是 live、
运行中窗口被关掉能报来源消失、停止后不留后台线程、对已消失窗口重开被拒绝。

## 已知不支持（不要当成已完成）

- **真实牌桌点数识别仍未通过。** 本机录像第 49222 帧：检出 16 个框，
  接受 0 个点数。原因有二：牌太小（浏览器窗口 1218×840 时整个牌阵只有
  730×140，点数约 10–14 像素高），以及 `navy_cards.py` 现在拿
  Hershey 字体当模板，和真实扑克字形无关。
- 座位归属未核对：探针把 16 张牌全归到「玩家4/5/6」，
  `navy_live_felt_v1` 的座位框与实际牌阵不符。
- 尚未接实时预览界面、区域/座位标定界面与自动确认；
  本轮只到「帧能稳定拿到并进识别管线」。
- 未验证：多显示器、DPI 中途变化、受保护内容黑屏、长时间稳定性。
- 未在真实牌桌窗口上做过连续捕获（本轮只在静止 Chrome 与自建测试窗口上实测）。
