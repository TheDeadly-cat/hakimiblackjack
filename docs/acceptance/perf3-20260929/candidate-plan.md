# PERF-3 C：固定候选复验与条件后备方案

固定候选由本分支 HEAD 的 Git 文件树导出，保留原 RC3 运行包、原冻结输入、历史失败和真实数据。
交付资料另存至独立试用目录；本分支及上游 PR 保持 Draft，不合并 main、不建 Release/标签。

复验顺序：核心检查/原生求解准备、完整 Windows 回归及原始 handoff；再独占运行同输入规模与三靴低干扰测试；
最后独立原生键盘操作及三类资料备份恢复。测试数据均新建，不能让多个性能运行互相争抢机器。
原始 profile 与正常延迟分开，三靴、1k、5k、10k 单独列示。快照、数值、状态、归属及旧历史不变各有对应断言。

最终外部回执须列出 tested_head、package_hash、actual_module_root，分别给出 validation_passed 与
latency_targets_met（150ms 录牌 p95、200ms 心跳 p99），并保留取消/失败请求、文件增长、未执行项及支持规模。
完整数据使用本机新证据目录，不把旧 RC3 的 CI 或人体长按结果重新签作本候选。

## B4 条件后备设计（本候选不实现）

只有 B1～B3 实测仍超过目标时才启用下一项开发。先以 profile 划清剩余同步 replay、完整基线读取、
计划 fsync 和界面绘制的成本。单写入者解决界面占用，不自动缩短耐久提交时间，也不能将“排队成功”当成已保存。

- 所有账本、计划和 SQLite 写入由一个有序执行器拥有；其线程内创建/关闭自己的连接。
  Tk 线程只接收不可变的结果和提交回执，不把现有 controller/connection 直接跨线程共享。
- 每项输入包含 command_id、会话/靴/轮、录入方式、点数/花色，以及所依赖的前一条命令和原目标身份。
  不使用 latest-wins。尚有前驱待提交时，必须用独立、明确标注的“待录位置”表达后继目标，不能拿旧已提交光标猜下一人。
  自动揭示/结算/开轮会改变目标的边界，在前驱回执确定前暂停接收下一目标的牌，保留已排队项并提示核对。
  不实现这套目标协议前，不允许开启快速输入队列。
- 工作线程逐条校验前驱和冻结身份，执行现有隔离候选/原子提交；同 command_id 返回原回执。
  任意失败保留失败项与后继项，不静默重试、跳过或转移给新座位。用户明确修正/取消后才续行。
- UI 分开显示待提交和已提交；任何待提交牌不进入已确认概率快照，旧推荐立即失效。
  成功回执后才公布牌面和持久光标；重绘失败仍标记“已保存”，不得诱导再次输入。
- 与现有 ExitFlow 对接：关闭时停止接收新命令，等待当前事务和已接收队列排空；
  如允许取消，只能明确取消尚未提交的尾部并显示数量。SQLite 事务中的写入不能被 UI 强制截断。
- 开始实现前补充真实队列测试：等值连续键/长按、七人目标、分牌两手、揭示自动开轮、
  Backspace 与换靴顺序、第二/第三条插入失败、磁盘满、恢复回执与关闭期间保存。

若本候选达到声明支持规模的目标，不实施该后备方案。若未达标，交付实测限制，并仅把上述协议的最小实现作为下一单。
