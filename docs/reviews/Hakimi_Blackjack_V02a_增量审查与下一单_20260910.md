## 4. 已经实现的产品价值

新链路：

```text
手动录牌 → 事件前缀重放 → 分析资格检查
→ 不可变 AnalysisInput → 独立计算进程
→ 条件概率/单手动作 EV → 中文显示
→ 独立分析快照 → 原时点读取/按前缀复算
```

核心实现与判断：

| 区域 | 证据 | 判断 |
|---|---|---|
| 输入资格 | `analysis/information.py::build_input` | 不是把剩余牌数直接送入算法；检查规则、烧牌、隐藏牌、参与者和手牌状态 |
| 条件概率 | `analysis/probability.py::FiniteModel` | 把正常未知底牌边缘化，负 BJ 检查改变下一次目标抽牌分布 |
| 动作 EV | `analysis/actions.py::solve_counts` | 补牌后继续按共同可见信息选择补/停，不按实际暗牌分别优化 |
| 部分比较 | `analysis/service.py::calculate` | 分牌合法但未实现时不给全局最优，全部负 EV 不包装成开局优势 |
| 异步生命周期 | `analysis/service.py::AnalysisService` | 已有独立进程、请求身份、预算、取消及输入摘要，不需要重新建设一套服务 |
| 历史分析 | `storage/analysis_snapshots.py`、`controller.py::recompute_input` | 原快照不覆盖、原前缀摘要检查、版本分离；无需先迁移 SQLite 结构 |
| 界面 | `ui/analysis_panel.py` | 真实数值、计算/超时/未支持状态、历史复算已接入 |

首发范围明确限定：6/7/8 副、有限不放回、从完整新靴开始、明确零初始烧牌、S17、3:2、美式底牌、A/T 明牌的必要非 BJ 检查、单参与玩家、单手未分牌。H17、6:5、非零烧牌、分牌 EV、多玩家 EV、识别与捕获未交付，属于声明范围外，不因未实现它们否定 V0.2a。

## 6. 新发现与修复要求

### R1 / P1：未结算结束丢失观察完整性信息

**证据：** `ledger/ledger.py::replay` 的 ROUND_ENDED 分支（位于已查阅的原文件 290—560 行片段），`analysis/information.py::build_input`，`core/table.py::start_round`。

`settle=False` 时不进行结算校验，结束分支只设置“已结束未结算”和 `unsettled_rounds`。它不因缺少初始牌等可证明的不完整情况标记 shoe gap。下一轮重置玩家手牌；分析入口检查当前 gap/pending/unrevealed，但没有恢复上一轮漏录信息。

复现提案：

1. 创建 6 副研究模板，第一轮只有玩家1参与。
2. 录庄家 9、8；玩家1只录 10，实际第二张初始牌未能记录。
3. 选择未结算结束，原因填写“玩家第二张初始牌漏录，无法补齐”。
4. 开下一轮，录玩家10、6；庄家10与一张暗牌，确认非 BJ。
5. 当前代码路径仍符合 build_input 检查，可能将漏录牌仍计在剩余组成中并发布精确分析。

**影响：** 同一靴后续概率基于错误的牌数/组成条件。这不是算法求和精度问题。

**修复：** 独立表达“结算是否完成”和“观察是否完整”。明确漏牌、未知是否有漏牌时，允许继续记录但不恢复精确分析资格；仅缺赔付/暂不结算而观察完整的轮次不应一律封禁。缺失字段的旧结束记录不能静默推导为观察完整；保留原事件并做保守诊断，格式扩展需明确兼容策略。不得解析一句自由文本原因来决定数学资格。

**验收：** 漏录→未结算→新轮必须阻止精确分析；完整观察但不结算的对照可按契约保留资格；恢复、导入、撤销/纠错与重放结果一致；不能仅关闭“未结算结束”按钮规避问题。

**状态：** 高置信度静态发现；对应交接测试尚未在完整仓库执行。

### R2 / P1：结果失效依赖 UI 刷新成功

**证据：** `ui/controller.py::_apply`；`ui/app.py::refresh_all`（805 行起）、`refresh_actions`、`fail`；`ui/analysis_panel.py::on_context`、`_poll`。

控制器提交成功会更新账本和 commit_revision，但分析上下文失效发生在 refresh_actions 调用 on_context 时。refresh_all 先执行 refresh_hands 和 refresh_table。任何前置刷新异常，或 refresh_all 整体异常，会导致 on_context 不执行。

_poll 只比较缓存的 request_key 与 context_key；两者尚未更新时，即使真实账本已变，旧请求仍可能通过比较。已显示的 last_result 也可能未被清除。fail 虽正确提示已保存，却没有使分析结果失效。

**修复：** 把数据版本改变与旧分析失效绑定，而不是绑定视图重绘；结果发布前再读取真实提交版本与目标标识核验。历史复算需要明确历史目标，不能为了拦旧结果一并禁止合法历史重算。补齐完成结果与进行中请求两种路径，并处理恢复/导入/切目标等上下文变化。

**验收：** 在旧结果已显示和旧请求仍运行两种情况下，成功提交新牌同时注入刷新异常；数据库只增加一次，提示已提交，旧数值立即清除或显著标旧、不可作为当前结果发布。刷新恢复后新请求使用新前缀。

**测试缺口：** 仓库现有 `test_refresh_failure_says_committed_and_io_failure_says_not_committed` 只断言消息与 DB 数量，未同时断言计算结果失效。

**状态：** 高置信度静态发现；两项交接回归尚未在完整仓库执行。

### R3 / P2：取消没有清理自动计算的延迟回调

**证据：** `ui/analysis_panel.py::on_context` 调用 after(250, calculate_current)；cancel 仅取消 service，没有 after_cancel(_auto_id)。自动复选框也没有清理已排队回调的处理。

**触发：** 自动开启，输入变化后处于250ms等待窗口，用户点击取消或关闭自动；此前排队的自动计算仍可能开始。

**修复和验收：** 取消/关闭自动时同时清理未执行回调；状态不变时不得自行重启，之后显式点击计算或按契约发生新输入时才能启动。与 R2 合并为一项生命周期修复，勿另起框架重构。

**状态：** 静态确认，交接用例只做语法检查。
